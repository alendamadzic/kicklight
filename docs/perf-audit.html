Why Kicklight feels slow

The code itself is fast. The time goes on where things run and the order things happen in. Every screen ships an empty shell, then downloads ~280 KB of JavaScript, then starts asking for its data, and each of those requests flies from London to Virginia and back to London again before anything shows. Fixing the region, the auth check and the data waterfall should take most first loads from seconds to well under one.

What to do, by impact

Tier 1 · Where requests go

Small changes, the biggest wins. Do these first.

1

Run functions in London, next to Supabase

Huge impact1 line

Set the function region to lhr1 (a vercel.json with "regions": ["lhr1"], or the project's Functions setting). Today every API call, every server render and every proxy run executes in Virginia, and each Supabase call from there is another ~80 ms round trip back to London.

Why it matters: a signed-in API call makes 2–3 Supabase calls (proxy auth, route auth, query). That is roughly 250 ms of transatlantic waiting per request that simply disappears.

2

Stop calling Supabase Auth on every request

High impactSmall

src/proxy.ts runs auth.getUser(), a network call, for every page, every API call and every link prefetch. Routes then call it again in requireUser(). The project already signs tokens with ES256 keys, so auth.getClaims() verifies the session locally with a cached public key and no round trip. Use it in the proxy and in requireUser(), keep the proxy only for refreshing an expiring cookie, and drop public routes (/api/matches, /api/config) and prefetch requests from its matcher.

Why it matters: removes 1–2 auth round trips from every signed-in request, and lets the CDN serve public API responses without a function in front of them.

3

One cached fixtures load instead of 22 requests

High impactMedium

Move the per-league fan-out to the server: a getFixtures(date) function that fetches all leagues in parallel, marked "use cache" with a short cacheLife on today (about 15 s) and a long one on yesterday and tomorrow. Everyone shares the same cached result, so ESPN is asked once per window instead of 22 times per visitor. The 30 s poll then becomes one request too.

Why it matters: 22 cold function invocations on first load is the single biggest reason Matches feels slow to fill in.

Tier 2 · Render data on the server

Turn on Cache Components and remove the client waterfall.

4

Enable cacheComponents and stream data into the first response

High impactMedium–large

Turn on cacheComponents: true. Each page keeps its static shell (served instantly from the edge) and gets a <Suspense> hole that streams the cached data in the same response. Matches renders getFixtures(); the match page renders the ESPN snapshot. Pass that into the existing SWR hooks as fallbackData, so polling and Realtime keep working exactly as now, they just start full instead of empty.

Why it matters: data shows before the JavaScript has even loaded. Bonus: with Cache Components, Next keeps recently visited tabs alive with React <Activity>, so switching Matches → Remote → Matches is instant and keeps scroll and filters. This needs a check of anything that assumes a page unmounts (open sheets, the strip animation loop, intervals).

5

Seed who you are from the server

Medium impactMedium

Today auth, preferences and the live session all start loading only after hydration, one after the other, so the chrome flickers between signed-out and signed-in and ★ Mine fills in late. Read the claims, the preferences row and the live session row on the server (one dynamic hole in the layout, in parallel) and hand them to the client stores as their starting values.

Why it matters: removes a client round trip chain of 2–3 Supabase calls and the layout shift that comes with it.

6

Make the landing page static

Medium impactSmall

/ renders on the server on every visit just to redirect signed-in users. Do the redirect in the proxy from the verified claims and let the landing page prerender. 447 ms to first byte becomes an edge cache hit.

7

Cache the match summary for the UI

Medium impactSmall

/api/matches/[league]/[id] has no cache header and ESPN is fetched with no-store. Wrap the UI's read in "use cache" with a ~10 s life (or add s-maxage=10), so every phone watching the same match shares one fetch. Leave the cron tick reading fresh.

Tier 3 · Ship less JavaScript

Matters most on phones, where parse time is the cost.

8

Load Supabase only when it is needed

Medium impactMedium

The tab bar subscribes to the live session, so the whole Supabase client (auth, Realtime, PostgREST) is in the shared bundle of every page, including Landing, Demo, What the lights do and 404. Import it with await import() inside the stores' start(), after the user is known to be signed in. Once auth comes from the server (#5), signed-out visitors never download it.

9

Lazy-load what isn't on screen

Low–mediumSmall

Nothing in the app uses dynamic imports today. Good candidates: the ⌘K search dialog (cmdk) on Matches, the kit picker and sheets in Setup, the moment overlay, and the onboarding steps after the first. Each one only needs to load when it opens.

10

Drop the /api/config request

Low impactTiny

The app mode and site URL never change for a deployment. Render them into the layout (or read them from NEXT_PUBLIC_ variables) instead of fetching them on every visit.

11

Trim fonts

Low impactTiny

Three Google families load on every page. Keep Barlow Condensed preloaded since it is the scoreboard, and set preload: false on Geist Mono, which only appears in a few secondary spots.

Suggested order

  1. Measure first. Add Vercel Speed Insights so we have real-user LCP and INP before and after.
  2. Tier 1 as one small PR (#1, #2, #6, #10). Low risk, and should already halve signed-in load times.
  3. Cache Components across the app (#3, #4, #7): turn it on, move fixtures and match data to cached server functions, and check every page with kept-alive tabs.
  4. Seed auth and preferences from the server (#5).
  5. Bundle work (#8, #9, #11), checked with a before and after build.

Decisions

Users are mostly UK and Europe

Functions move to London (lhr1), next to Supabase.

Cache Components for the whole app at once

Turned on everywhere in one pass. Every page gets checked for the kept-alive tabs behaviour.

Fixtures may lag by up to about 15 s

One shared cached load per window. The remote stays real time over Realtime.

Measure first

Speed Insights goes in before anything else changes, so we have a baseline.
